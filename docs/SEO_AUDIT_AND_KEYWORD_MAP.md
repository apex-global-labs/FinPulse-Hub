## Metadata / FAQ / content-depth interpretation

1. **Title template:** currently programmatic and tool-name-led. It is unique enough to distinguish many pages, but not optimized to reflect distinct intent, inputs, output and audience. Avoid “Instant & Accurate” where the result is an estimate or user-entered assumption.
2. **Description:** generated from the tool description with a shared sentence; unique wording is partly inherited from `d.desc`, but it is not a researched conversion-focused snippet. Write concise, specific descriptions (roughly 140–160 characters where natural) with one clear benefit.
3. **Canonical:** current `?tool=` routes are internally consistent with sitemap. Query URL is not inherently invalid; do not migrate without route-level validation.
4. **FAQ:** schema is generated from visible FAQ content, which is good parity practice. Presence is not the same as quality; generic FAQ repetition across many tools can create low-value duplication.
5. **Guides:** include formula, variable definitions, units, a worked example, assumptions, exclusions and use cases only where they genuinely help. For simple counters/converters, concise unique explanations may be better than an artificial 500-word essay.

## Priority bands and execution order

- **P1 (78–95):** high-intent or broadly useful queries with clear task completion; prioritize first for content and static-render prototype. This is not a promise of easy rankings.
- **P2 (65–77):** valuable supporting or niche tools; build after P1 prototypes and after verifying the intent is distinct.
- **P3 (45–64):** narrower, specialized or higher-maintenance intent; publish only with accurate formulas, a clear audience and useful explanatory content.

**Recommended pilot order:** Mortgage Calculator, Percentage Calculator, Age Calculator, Length Converter, Word Counter. These cover a complex finance calculator, simple arithmetic intent, date logic, unit conversion and text utility. They are representative of materially different rendering and content requirements.

## Static prerender feasibility — prototype acceptance criteria

A static build should emit an HTML document for each selected route with a meaningful title, description, canonical, H1, calculator shell, formula/guide text, visible FAQ and JSON-LD already present in the initial HTML. Client JS may then hydrate/attach controls.

Prototype must pass:
1. Direct-load and refresh on each route on GitHub Pages.
2. Existing `?tool=` route remains functional during migration; no premature canonical flip.
3. Unique initial HTML title, description, canonical and tool-specific body content without waiting for client JS.
4. Calculator works after JS loads; formula outputs match existing regression tests.
5. Browser back/forward, search, category navigation, share links and query input state remain intact.
6. Embed mode remains isolated and functional; no accidental ad/analytics or duplicate navigation inside iframe.
7. Sitemap URL parity, canonical parity, no duplicate indexable URL variants.
8. Mobile layout, accessibility, CSP and performance budget remain within the existing release guardrails.
9. Compare initial HTML and rendered DOM using curl/source inspection plus Playwright; test a JS-disabled crawler view.
10. No paid service, backend or runtime dependency is introduced.

**Architecture direction:** use a zero-cost Node build script in GitHub Actions to produce static route folders/pages from the existing registry. Keep one source of truth for tool metadata. Avoid hand-maintaining 220 HTML copies. The current query URL format can coexist during the prototype; pretty URLs should be a later, separately approved migration.

## Country and localization rules

- Finance pages: global English by default only where the formula is jurisdiction-neutral. Mortgage, auto, student and personal loans must state that fees, APR rules and lender practices vary.
- Tax/payroll pages: explicitly identify the supported country/state and tax year. Current source descriptions include 2026 jurisdiction or user-entered flat-rate assumptions; do not market them as universal tax calculators.
- Currency and transfer pages: use global pair intent, but disclose reference-rate date, provider fees and that reference rates are not live executable quotes.
- GPA/grade pages: distinguish US 4.0 and Bangladesh 5.0 profiles; do not imply a universal grading scale.
- Construction pages: metric/imperial support does not make local codes, material sizes or mix standards universal.
- Health/wellness pages: keep informational/user-entered framing; no diagnosis, prescribed target or unsupported health claims.

## Existing related-tool strategy

Current source selects a small set of same-category tools. Replace this with explicit `relatedToolIds` metadata, prioritizing:
- same user task (e.g. mortgage payment → affordability → payoff → refinance → amortization);
- adjacent calculation stage (e.g. percentage → discount → sales tax → tip);
- complementary format/utility (e.g. word count → character count → reading time);
- category hub and one cross-category link only when contextually justified.

Do not link every page to the same generic “popular tools” list. Related links must be useful, crawlable HTML anchors, and avoid cycles that add no user value.

## Risks and safeguards

- Do not create 220 near-identical pages with only keyword swaps.
- Do not create city/country doorway pages. Localized pages need genuinely different formulas, data, dates and supporting sources.
- Do not promise “accurate”, “best”, “instant” or financial outcomes beyond what the calculation supports.
- Do not stuff every synonym into title, description, headings or FAQ.
- Avoid publishing a tool-specific guide until the formula, units, assumptions and exclusions are reviewed.
- Keep financial inputs local; do not send entered financial values to analytics.
- Keep health tools informational and clearly disclaimed.
- Do not place ads where they obscure calculator controls or create accidental clicks.
